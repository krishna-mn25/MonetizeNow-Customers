The Causal Chain — Read This First

Every Xage HubSpot issue traces back to one architectural decision and one sequencing mistake. They are not 10 separate problems — they are 2 root causes creating 10 symptoms.

ROOT CAUSE 1: Line Item Truncation (Architectural)

MN quote has real qty, unit price, billing freq → HS connector forces qty=1, price=total blob → Xage hires SimpleStrat to build HS workflow → Workflow reads monetize_quoteitem_* custom props → Corrects native HS line items ✓

ROOT CAUSE 2: Re-Sync After Correction (Sequencing)

Xage closes deal as Closed Won in HS → SimpleStrat workflow fires, corrects line items → Heather then processes quote in MN → MN fires Quote.Processed webhook → full resync → Overwrites corrected values with truncated blob again

COMPOUNDING: The Workflow's Fix Creates a New Vulnerability

SimpleStrat workflow deletes MN's line items → Recreates them with correct values → But strips monetize_quoteitem_id + monetize_quoteoffering_id → Next MN sync can't find existing items → creates DUPLICATES

So: MN sends bad data → Xage builds workaround → workaround conflicts with MN's re-sync behavior → workaround breaks MN's dedup keys → duplicates appear → trust collapses.

1
Line Item Truncation — The Structural Root
This is WHY everything else exists
› What MN Actually Sends to HubSpot (Codebase Confirmed) Connector Code Structural
The Code (HubSpotSyncService.kt / package.kt)
// package.kt:778–798 — CrmSyncType.HubSpot.LineItem.transform() // Comment from source code: // "Due to HubSpot preventing us from overriding the native pricing fields // (they are calculated fields), we work around this by always setting the // quantity to 1 and the price to the total price of the line item." unitPrice = quoteItem.amount // → HS native "price" = total blob quantity = 1.0 // → hardcoded, always
What This Means
HubSpot's native line item fields are calculated: amount = quantity × price. You can't override amount directly. So MN forces qty=1 and price=total so that HubSpot's own math produces the right deal-level rollup.
What IS Preserved (Custom Properties)
The real values survive in monetize_quoteitem_* custom properties on the line item: monetize_quoteitem_quantity (real qty), monetize_quoteitem_unit_price, monetize_quoteitem_unit_price_after_discount, monetize_quoteitem_amount, monetize_quoteitem_amount_without_discount, plus ARR/MRR, discount %, product type, etc.
What Is NOT Preserved Anywhere
Billing frequency / term cadence. There is no native billing-period field on the HS line item at all. MN only writes hs_recurring_billing_start_date and hs_recurring_billing_end_date + the lump price. The billing cadence (annual, quarterly, bi-annual, 34-month — whatever the MN rate says) is not represented. The constrained enum (monthly/quarterly/per_six_months/annually) only exists on the Product object, not the line item.
Why Xage Cares
Xage's sales ops and board reporting run on HubSpot. A line item showing "1 × $150,000" instead of "100 licenses × $1,500/yr" makes their deal data opaque. They need per-unit economics, real quantities, and billing terms visible natively for forecasting, commissions, and pipeline hygiene. The custom properties exist but aren't surfaced in HubSpot's standard deal views or reports without custom work.

The SimpleStrat Workflow — The Workaround That Creates New Problems
Pylon #4645, #4498, Fathom May 11
› What the Workflow Does HubSpot High
The Bridge
Xage hired SimpleStrat (Ryan) to build a custom-coded HubSpot workflow that runs when a deal reaches certain conditions. The workflow reads the accurate values from MN's custom properties (monetize_quoteitem_quantity, monetize_quoteitem_unit_price, etc.) and writes them into the native HubSpot line item fields so that reports/views show real data.
The Fatal Flaw
The workflow appears to delete the original MN-synced line item and recreate it with correct native values. But in doing so, it strips the monetize_quoteitem_id and monetize_quoteoffering_id fields. These are MN's deduplication keys. Without them, the next time MN syncs (for any reason), it sees no existing line item with a matching quote item ID and creates a brand new one → duplicate line items appear on the deal.
Confirmed by Engineering
Huy Ngo (MN Eng, May 14): "Yes, if the fields that we depend on have their values removed, we can't deduplicate so we end up creating more line items."
The Trap
The workflow is simultaneously essential and destructive. Without it, Xage has meaningless line items. With it, they lose MN's sync integrity. There's no middle ground with the current approach.
› The Sequencing Conflict (May 11 SimpleStrat Call Root Cause) Process Escalated
Xage's Business Process
Most MN customers: Process quote → Close deal. Xage does the reverse: Close deal as Won → then process quote in MN. This is because their internal review (PO vs. sales order form) requires deal closure in HubSpot first.
What the Code Actually Does (Verified)
Contrary to what Kevin told Heather ("we don't sync back after Processed"), the codebase shows: the connector imposes NO post-processed lock. Every Quote.Update and Quote.Processed webhook triggers a full deal + line-item reconciliation. The PROCESSED check in the code is additive (writes PDF, contract props), not a gate. So when Heather processes the quote after Closed Won, MN fires a webhook, the connector runs syncQuoteOfferings(), and it overwrites whatever the SimpleStrat workflow just fixed.
The May 11 Agreed Fix
On the 3-way call (Krishna, Ryan, Heather), the group agreed: trigger the SimpleStrat workflow after the quote reaches "Processed" status in MN, not after "Closed Won." Since MN's last sync fires on the Processed event, the workflow running after that becomes the final authority. This was tested on the Orange Cyber Defense Norway deal ($5,377) and confirmed to work.
Blocker identified on May 11: Xage has a required co-signer step in MN between Accepted → Processed. This prevents API automation of the Processed status, forcing Heather to manually move each quote. Krishna committed to prioritizing removing the co-signer requirement. Status: Unknown — needs verification before tomorrow's call.
Why This Fix is Fragile
Even with correct sequencing, any subsequent MN event that triggers a quote webhook (expiration, amendment, any update) will re-sync and overwrite again. The May 26 call confirmed exactly this: a quote expiration triggered a re-sync and created duplicate line items on an already-closed deal. The sequencing fix only works if MN never touches the deal again after the workflow runs. That's not guaranteed.

The Real Diagnosis — Where Our Solutioning Failed
› Why the SimpleStrat Workaround Was Doomed From the Start Root Cause
The Fundamental Error
We told Xage: "The real values are in the custom properties, use those to fix the native fields." This sounds logical. But it ignores the fact that MN's connector treats line items as its own managed objects — it diffs, creates, updates, and deletes them on every sync event. Any external process that modifies those objects is working against MN's reconciliation loop. The SimpleStrat workflow is effectively fighting the connector for ownership of the same data.
The Three Things We Got Wrong
1. We told Heather "we don't sync after Processed" (Kevin, #4498, Apr 30). The codebase proves this is wrong. syncQuote() has no status guard. The only thing that stops sync is: the quote isn't the primary quote, or it's a migration quote. This misinformation shaped Xage's entire workflow design around a false assumption.
2. We never warned about deduplication keys. When SimpleStrat built the workflow, nobody told them that monetize_quoteitem_id and monetize_quoteoffering_id are critical dedup keys. If the workflow deletes and recreates line items (which is the natural HS workflow pattern), those keys vanish, and MN will create duplicates on next sync. We knew this (Huy confirmed it immediately when asked), but nobody proactively communicated it.
3. We treated the symptom (bad line item values) instead of the system interaction. The right question was never "how do we fix the line items after MN sends them" — it was "how do we make MN and HS agree on who owns line item data." We let an external workflow fight the connector instead of designing a data ownership boundary.
What An Expert Would Have Done Differently
Instead of telling Xage to build a corrective workflow (which fights the connector), the right approach would have been one of:
Option A — Workflow Preserves Dedup Keys: If SimpleStrat's workflow must run, it should UPDATE the existing line items in place (not delete + recreate). This preserves monetize_quoteitem_id and monetize_quoteoffering_id. MN's next sync will find matching items and UPDATE them (overwriting the corrected values, yes — but if the workflow triggers after the last MN sync, it gets the final word). The workflow must be an UPDATE, never a delete-and-recreate.
Option B — MN Stops Syncing After Processed (Code Change): Add a status guard in syncQuote() or syncQuoteOfferings(): if the quote is already Processed, skip line-item reconciliation. This makes Processed a true lock. Xage's workflow becomes the permanent authority. This is the cleanest fix but requires product team involvement.
Option C — MN Sends Correct Values (The Real Fix): Write real quantity and real unit price to the native HS fields. Yes, this means amount (quantity × price) might differ from the MN total if discounts are applied. But you can set discount on the line item to compensate. Or accept the rollup discrepancy and let Xage use monetize_quote_arr for the deal amount via a simple HubSpot workflow (most MN+HS customers already do this). This eliminates the entire workaround chain.

Verdict — Is This a Product Gap or a Solutioning Gap?
› It's Both — But the Solutioning Gap Is the Bigger Failure
The Product Gap (Real, But Known)
HubSpot's calculated line item fields force the qty=1/price=blob pattern. This is a real platform constraint that MN chose to work around rather than fight. Every HS customer is affected, though most don't notice because they don't run HS workflows on line items. The product gap is: MN should write real values to native fields and accept the rollup trade-off (use deal-level custom props for accurate totals).
The Solutioning Gap (Where We Failed Xage)
We had all the pieces. The custom properties carry real values. The connector has clear dedup behavior. The webhook events are documented. The sync lifecycle is well-defined in code. But we never connected these dots for Xage or SimpleStrat. We:

— Let a third party build a workflow against our connector without being in the design room
— Gave incorrect information about post-processed sync behavior
— Didn't proactively communicate dedup key requirements
— Treated each ticket as isolated instead of seeing the pattern
— Proposed a sequencing fix that doesn't account for expiration events

The information existed. The solution was possible. We just didn't assemble it correctly.
The Fix Is Available Without Product
Step 1: Redesign SimpleStrat workflow to UPDATE (not delete/recreate). Preserve dedup keys.
Step 2: Trigger on Processed + Expired + any other terminal status.
Step 3: MN provides full property map + dedup key documentation to Ryan.
Step 4: Auto-renewal decoupled via custom field (already in progress).
Step 5: Joint MN + SimpleStrat session to validate the complete flow end-to-end.
Step 6 (optional, product): Request a syncQuoteOfferings guard: skip line-item sync when quote status is Processed or Expired. This makes the fix bulletproof.
