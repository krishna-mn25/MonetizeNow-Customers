Usage billing for Affinity.
The full picture.

This document covers how MonetizeNow handles usage-based billing, what Affinity's engineering team needs to build, and every decision that shapes implementation. Written for anyone on the team, whether you've used MN before or not.

What Affinity Wants to Do
Start charging customers who exceed their included API call limit (100K/mo on Scale, 250K on Advanced, etc). Overage rate: $1.50 per 1,000 calls. Customers can also pre-buy call bundles at discounted rates to avoid overage pricing. Target: July launch with new business, existing customers amended when they hit limits.
Why This Doc Exists
MonetizeNow handles billing: calculating charges, generating invoices, collecting payment, syncing to Salesforce. But MN needs to know how many API calls each customer made. That data lives in Affinity's product. So this doc covers: how billing works in MN, what eng needs to build to connect usage data, and decisions that shape the rollout.

How this maps to MN
Platform fee = subscription product, billed in advance (already in MN, no change). Included allotment = usage product with a Bucket that holds the included pool. Overage = tiered pricing on the same usage product. First tier draws from the bucket, overage tiers bill per-unit. Pre-paid bundles = pre-paid credit product. Draws down against usage until depleted, then normal pricing continues.
Phase 1 (July) is simpler
Just API call overages on existing tiers. No min commit, no Agentic Tasks yet. Full packaging revamp with min commits and multiple usage metrics is Phase 2 (later this year). One min commit can cover multiple usage metrics by scoping it to specific products. One min commit offering per quote, one min commit product per offering.

Allotment translation
Your tiers express included usage in units ("250K calls/mo"). MN models this via a Bucket (not a simple quantity field). The included allotment becomes a Bucket with a monetary value. First pricing tier draws from the bucket; overage tiers bill per-unit at $1.50/1K. Customer-facing output can display unit counts while MN runs on dollar values underneath.
Arrears billing confirmed

3The Full Billing Journey: Quote to Invoice
Purple steps = what Affinity engineering builds. Everything else is MN or already exists in your product.
1
MonetizeNow
Rep builds a quote with platform + usage offerings
Sales rep creates a quote in MN with platform license (existing) and new API Usage offering. If customer wants a pre-paid bundle, that goes on as a third offering. Quote shows all terms, rates, and billing schedule.
2
MonetizeNow
Quote is processed. Contract + Subscriptions created.
When the quote is processed, MN creates a Contract. Each offering becomes a Subscription with a unique subscriptionId. This ID is how MN knows which customer's usage belongs where. Platform invoice fires right away (advance). Usage subscription starts tracking but no invoice yet (arrears).
3
Affinity Product
Customer uses Affinity's API. Your product tracks the calls.
This already happens today. Affinity enforces the 100K call limit, which means you're already counting API calls per customer. That existing data is the source for billing. No new tracking needed.
4
Eng Builds: Customer-to-Subscription Mapping
Your system needs to know which MN subscriptionId belongs to which customer.
One-time setup. For each Affinity customer with a usage contract, store the mapping between your internal customer ID and MN's subscriptionId. Recommended: store your customer ID as a custom field on MN Account, then look it up via MN's API before each push.
Your mapping table: affinity_customer_id | mn_subscription_id cust_acme_corp | sub_8f3a2b1c cust_summit_partners | sub_9d4e5f6g
5
Eng Builds: Push Usage Data to MN
At your chosen cadence, send each customer's API call count to MN's Usage API.
Your code posts one record per customer per period. MN needs these fields:
{ "subscriptionId": "sub_8f3a2b1c", "productId": "prod_api_calls", "quantity": 47521, "periodStart": "2026-07-01T00:00:00Z", "periodEnd": "2026-07-31T23:59:59Z", "externalId": "aff_acme_202607" } externalId = your dedup key. If you POST the same externalId twice, MN ignores the duplicate. Safe to retry.
6
MonetizeNow
MN stores usage records and waits for billing period end.
MN receives your usage records and stores them per subscription. No invoice fires yet. MN just accumulates the data until the configured billing period ends (monthly or quarterly, Brian to decide).
7
MonetizeNow
Billing run fires. MN aggregates usage and calculates charges.
At configured cadence, MN aggregates all usage for the period (sum of all calls). Applies block pricing: first tier against included allotment, overage at $1.50/1K. If pre-paid credits exist, draws from those first (draws down to zero, then normal pricing continues). Rate is locked at contract creation, not retroactive if changed mid-period.
8
Output
Invoice generated, tax applied, syncs to SFDC, sent to customer.
Arrears invoice with usage line items. Tax calculated via Avalara per product tax code. Invoice syncs to Salesforce (selected fields, not all MN data points). Note: usage records are stored in MN and accessible via API, but don't all flow into SFDC automatically. Your Fivetran/Redshift pipeline pulls from SFDC, so it would only capture what MN syncs there.
Engineering builds steps 4 and 5 only
Everything else is MN out of the box or already exists in Affinity's product. Step 4 (mapping) is a one-time lookup table. Step 5 (push usage) is the ongoing integration. Three ways to do Step 5 on next slide.
4Step 5: Three Ways to Push Usage Data
Same result (usage records in MN), different levels of automation. Pick based on eng bandwidth for July.
Option A - Real-Time API
Push on Every Call
Affinity's product fires to MN on every API call (or in batches of 1,000). MN has a live tally at all times.
How it works:
1. Customer makes an API call
2. Your product increments the counter
3. Every 1,000 calls (or your preferred batch size), call MN's Usage API with the subscription ID and quantity
4. If the call fails, queue it for retry using the externalId for deduplication
5. MN stores the record. No invoice yet, just accumulating.
Eng effort: 2-4 weeks. Highest accuracy. Real-time dashboards possible.
Option B - Daily Batch
End-of-Day Totals
A scheduled job runs once per day. Tallies each customer's daily calls. Pushes one record per customer to MN.
How it works:
1. Scheduled job runs at 11 PM PT (or your preferred time)
2. Queries your usage database for each customer's daily call count
3. For each customer, looks up their MN subscription ID from your mapping table
4. Calls MN's Usage API once per customer with the daily total
5. Logs results: "Pushed 847 customers, 0 failures"

Must complete before MN's nightly billing run fires (we'll confirm exact time).
Eng effort: 1-3 weeks. 24hr lag but simpler. One job, one push.
Option C - CSV Upload
Manual Monthly
Someone exports monthly data, formats to MN template, uploads before billing run. No eng build needed.
How it works:
1. End of month: export usage from your database
2. Format to MN's CSV template (we'll share the spec)
3. Upload via MN's UI
4. Billing run picks it up and generates invoices

Human-dependent. If the person leaves, knowledge walks out. Doesn't scale past ~50 customers. No mid-period visibility.
Eng effort: zero. Ops cost is ongoing.
Brian's preference
"I just do not want to do the uploads." He's pushing for A or B. Our recommendation: Option B if eng time is tight, Option A if you can invest the extra week. Option C only as a validation bridge for the first month while API integration stabilizes.

It is supported. MN handles rebilling for usage and min-commit invoices. If a usage invoice needs correcting, you can use credit/rebill. We'll validate this in sandbox before go-live. As a backup, credit note + one-time invoice with a custom dropdown for "usage billing correction" also works.

Usage + Pre-paid Credits tax via Avalara?
Yes. Both flow through standard Avalara calculation unless explicitly marked exempt. Your new usage products will need Avalara tax codes assigned in MN's catalog.

Existing Contract Migration
Amend existing contract or create new?
Amend. No restriction on adding usage products via amendment. Keeps original billing schedule for continuity. Newly added products get prorated automatically. New contract would break the single billing timeline.
Confirmed
